Developer use case

Beyond a Second Screen: Building an AI Development Worker with an Android Tablet

A DOOGEE U12 plugged into a MacBook Pro as an extended display can also be a workstation that runs its own coding agents. UScreen gives the tablet the screen. Everything else — Termux, SSH, OpenCode, Syncthing — is ordinary, open tooling that the operator assembles by hand. The separation between those two halves is the whole point of this article.

  • Published 2026-10-31
  • The operator’s own setup, in daily use
  • UScreen = the display, nothing else
  • MacBook Pro · DOOGEE U12 · Galaxy S24 Ultra
What UScreen does, and what it does not. UScreen creates a genuine extended macOS display on the Android tablet, streams that display over the USB cable and returns touch to the Mac. It does not run AI models, does not distribute agents to other machines, does not synchronize project files, and it has no built-in AI worker feature. Everything in this article beyond the display is third-party tooling running on the tablet.

01 — The problem

Every agent session wants the same machine

Run several coding agents at once on one Mac and they all want the same two resources: CPU time and memory. The agent runtime, the language server, the build tools, the test runner and the model client all live inside the same machine as the editor, the browser and everything else you have open.

That is not a defect in any one tool — it is what happens when several genuinely parallel workloads share one set of cores and one pool of RAM. The usual answers are to run fewer sessions at a time, to keep the local model small, or to buy a second machine. The first two cost you the thing you wanted in the first place. The third costs money you may not have.

The move that worked here was different: keep the interface on the Mac and move the execution to hardware that already exists. Not a new machine — a tablet. It is smaller and slower, but it is idle, it is already on the desk, and it has a screen of its own.

02 — The unexpected opportunity

A tablet is a computer, not a panel

When people say “second screen”, they picture a passive rectangle. A modern Android tablet is not that: it has an ARM CPU with several cores, a few gigabytes of RAM, internal storage and a complete operating system with its own package management and permission model.

Termux gives that hardware a Linux-like userland on top of Android — a shell, a package manager, an SSH server, git, language runtimes and compilers. In that userland the tablet can hold a checkout of a project, run a coding agent, run the tools that agent calls, and keep working while the Mac is busy or asleep.

The catch, stated early: Android is not Linux. It uses Bionic rather than glibc, it has no systemd, and it puts its own limits on background work. Those limits are real and are listed further down — but they are limits of the platform, not of the idea.

03 — The real setup

The real setup, component by component

Two machines are doing the work here, and a third is kept in reserve. One component in this table is UScreen. The rest are third-party tools, and keeping that line sharp is what makes the setup understandable.

The components of the setup and the job each one performs
Component The job it does Whose
MacBook Pro The desktop, the keyboard, the editor and the browser. It is where the operator reads and types, and it stays responsive because it is no longer the machine doing the agent’s work. Apple’s hardware
UScreen for Mac Creates the extended display, captures it, encodes it, sends it down the USB cable and returns touch to the Mac. That is the entire scope of UScreen in this setup. UScreen
DOOGEE U12 Two roles at once: the physical extended display, and the machine that actually runs the agent and its tools. The operator’s hardware
Termux The userland on the tablet: shell, package manager, development tools, and the place the agent runs. Third party
OpenSSH (in Termux) The door between the two machines. The Mac logs into the tablet with a key, so the shell is unattended and the password never travels. Third party
Tailscale The private network that makes the tablet reachable from the Mac without exposing a port to any public network. SSH rides on it. Third party
Herdr A terminal workspace manager for AI coding agents. On the Mac it opens the session; over SSH it attaches that session to the tablet’s shell, so the agent’s output lands in a Mac window — which is then visible on the extended display. Third party
OpenCode The coding agent itself. It runs on the tablet, in the tablet’s project directory, and calls the model endpoint remotely. Third party
Git Version control on the tablet’s copy of the project, so the worker produces ordinary commits rather than a private mess. Third party
Syncthing Keeps the project directories the same on every machine, in both directions, without a central server. Third party
Remote model endpoint Where inference actually happens. The agent on the tablet orchestrates and runs tools; the model is called on the operator’s own AI computer, over the network. The operator’s existing infrastructure
Galaxy S24 Ultra A second, independent worker with its own copy of the project. The operator picks which device runs a session; nothing is scheduled automatically. The operator’s hardware
The division of labour in one sentence. UScreen provides the extended display. Termux, SSH, OpenCode and Syncthing provide the independent remote development workflow. The tablet is where those two halves meet — and they are separate halves, not one product.

05 — In practice

How it feels to use

  1. Plug in the tablet and connect

    UScreen creates the extended display; the operator authorises the session in the menu bar and the desktop extends onto the tablet.

  2. Open Herdr on the Mac

    The terminal workspace manager is the operator’s usual place for agent sessions. It runs on the Mac, next to the keyboard.

  3. Attach to the tablet over SSH

    Herdr opens a remote session against the tablet’s Termux shell over the private network. The prompt now lives on the tablet; the keyboard does not.

  4. Start OpenCode in the project directory

    The agent starts in the tablet’s copy of the repository, on the tablet’s CPU and memory.

  5. Type prompts on the Mac

    The Mac keyboard and the Mac’s own tooling stay in play; the work happens on the other machine.

  6. Watch the output in the window on the tablet

    The Herdr window is drawn on the extended display, so the agent’s output is visible on the tablet while the tools it calls run there too.

  7. Move the work if you want to

    The session is not tied to one machine. The operator can pick up the same project on the Galaxy S24 Ultra and continue there.

The display device and the compute device can be the same tablet. The Mac keyboard drives a terminal window that lives on the tablet’s screen, and the agent answering it runs on the tablet’s own processor.

That is the part that is genuinely unusual, and it is worth being precise about it. The tablet is not a remote display of a session that is really running on the Mac. It is a real second screen and a real computer, and the operator is using both roles of it at once.

06 — The files

Project synchronization (optional, and manual)

Syncthing keeps the project directories the same on the Mac, the tablet and the phone. It is a peer-to-peer tool with no central server, and the operator shares one folder per repository with the other machines. Files travel in both directions.

Three rules keep that safe in practice, and they are worth copying:

  • Device-local secrets stay out. The ignore rules exclude secret-shaped files that are not part of the repository, so a key or a token never travels to another machine by accident. Tracked files are always synchronized.
  • Generated dependencies and platform-specific binaries are local. Build output, dependency directories and native artifacts are rebuilt on the device that needs them; they are not copied around.
  • Git metadata is treated as local. A synchronized repository directory is not a substitute for a remote. Each device keeps its own history and talks to the remote the normal way, so a synchronization conflict can never rewrite committed history.
Two honest limits of file synchronization. It is not instantaneous — an edit can take seconds to appear on the other machine, and a worker that starts a few seconds too early can read a slightly older file. And it is not a merge algorithm: if two machines edit the same file before the change has travelled, the conflict is resolved by hand.

There is no scheduler and no exclusive project lock. Which machine runs the session is a decision the operator makes every time, and the synchronization layer is deliberately kept out of that decision.

One thing that does not travel, and that this article will not pretend otherwise: the agent’s own state. The conversation database of the coding agent and any agent-specific memory it keeps live on the device that produced them. They are not synchronized, and a session started on the tablet does not continue on the phone.

07 — Benefits

What this actually buys you

CAPACITY

More CPU and memory for supported work

Agent sessions and the tools they call run on hardware the Mac is not already using. This is real capacity, on a slower processor with less RAM than the Mac — not Mac-class performance.

MAC

Fewer agent runtimes on the Mac

The Mac keeps what it is good at: the editor, the browser, the terminal. It is no longer the machine on which every agent, language server and test runner competes.

REUSE

Existing hardware, used again

No new machine, no server rack. A tablet that was bought for reading and video becomes a worker with a display of its own.

WORKSPACE

One Mac-controlled workspace

The operator still types on the Mac, in the tools they know. The work simply happens elsewhere — and the output is visible on the extended display.

ISOLATION

Independent worker environments

A build that goes wrong on the tablet takes down the tablet’s session, not the Mac’s. Each worker has its own shell, its own tools and its own project copy.

SOURCE

The same source, everywhere

Through synchronization, the worker has the same project as the desk. The work continues on another device without a manual copy step.

What this does not do. It does not make the Mac’s memory pressure disappear — it moves part of the load to another machine. And it does not make an Android tablet as fast as a Mac. Both statements would be false, and both are worth stating before somebody builds a plan on them.
08 — Limitations

Limitations, stated plainly

This setup is worth copying because its limits are knowable in advance. Here they are.

  • Bionic, not glibcAndroid’s C library is not the standard Linux one. A tool that links against glibc-specific behaviour needs an Android-compatible build or a compatibility layer.
  • Some tools need other packagesCommand-line tools often exist in Termux under a different name or a different version than in a normal Linux distribution. What is available is not the same set.
  • Some tools are simply missingDevelopment tools that depend on kernel interfaces, or on desktop frameworks, are not available on Android at all. The worker is a second location for supported work, not a replacement for the desktop.
  • macOS-only frameworks cannot runAnything built on Apple’s own frameworks belongs on the Mac. The tablet can call the same tools over SSH; it cannot load them.
  • Background restrictionsAndroid limits what keeps running when the app is not in the foreground. A persistent session can be killed by the system when the screen goes off or the app is swiped away, and a wake-up has to be arranged deliberately.
  • Heat and batterySustained compile and test load throttles a tablet, and the tablet runs on battery. A long session is a warm device.
  • The display and the worker competeDecoding a video stream and running an agent’s toolchain on the same system-on-chip is two real workloads. They share memory bandwidth and thermal headroom.
  • Networking is separate workReaching the model endpoint from the tablet needs its own route — the private network, in this setup — and its own configuration. None of that comes with UScreen.
09 — Getting started

A safe order to build it in

Each step stands on its own, so the setup can be built and checked one piece at a time. The examples use placeholder names — dev-tablet and dev-host — because a public document should not carry anyone’s real host names, addresses or keys.

  1. Install UScreen and prove the display

    Do this first and on its own: install the macOS application and the Android receiver, connect the tablet over USB and confirm that a window can be dragged onto it and that touch comes back. Everything after this point assumes the display already works.

    The installation steps on this site · the installation guide

  2. Give the tablet a userland

    Install Termux on the tablet and add the pieces a worker needs: a shell, an SSH server and Git.

    pkg install openssh termux-services git
passwd                       # a password for the tablet account
sshd                         # start the SSH server

  3. Let the Mac in without a password

    Put the Mac’s public key into the tablet’s ~/.ssh/authorized_keys, then reach the tablet over the private network instead of an address on the open internet.

    ssh dev-tablet 'echo connected'   # dev-tablet is a Tailscale name

    Set the private network up first: Tailscale on both machines.

  4. Attach the terminal to the tablet

    With the shell reachable, Herdr can hold the session on the tablet while the window stays on the Mac.

    herdr --remote dev-tablet

  5. Start the agent in the project directory

    On the tablet, inside the checkout, start the agent. It runs where the files are, and it calls the model endpoint you configure for it — the tablet does not host a model.

    cd ~/projects/example
opencode

  6. Only then add the files

    Synchronization is the part that can surprise you. Add it once the worker is proven: install Syncthing on both machines, share one repository folder, and keep secrets and build output out of it.

One habit worth keeping. Test each step on its own before adding the next. The display is easy to check, the shell is easy to check, the agent is easy to check — and each one tells you plainly whether it worked.

10 — Closing

A second screen can be part of the machine

A second screen can be more than a display. With the right tools, the device behind that screen can become part of your development environment.

The setup works because the two halves stay separate. UScreen’s job is narrow and it does it properly: a real extended display, video over the cable that is already plugged in, and touch that comes back. The development-worker half is ordinary tooling — a userland, an SSH session, an agent, a folder — assembled by hand, on hardware that was already bought.

The tablet in this setup is not a second computer on the desk. It is the second screen, doing double duty, and the operator gets a workstation out of it without a second purchase.
