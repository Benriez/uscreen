01 — The short version

A display macOS believes in.

Most tablet-as-second-screen tools hand you a mirrored picture or a video stream inside an app. UScreen does what a physical monitor does: it registers a virtual display with the window server, the system lays windows out across it, and the pixels are captured, encoded and sent down the USB cable.

EXTEND

Extended, not mirrored

Windows can be dragged onto the tablet. The menu bar, Mission Control and window layout treat it as another screen, because it is one.

CAPTURE

Native capture pipeline

ScreenCaptureKit captures the display; VideoToolbox encodes H.264 with the media engine. No ffmpeg child process, no software encoder in the default path.

INPUT

Touch returns to the Mac

Taps, drags and two-finger scrolling on the tablet become real pointer and scroll events on the Mac, mapped to the virtual display's geometry.

TRANSPORT

One cable, local only

Video and input travel over adb reverse on loopback ports. Nothing is exposed to the network, and no cloud service is involved.

LIFECYCLE

Display that cleans up

The virtual display is removed when the host exits, and an independent supervisor watches the session and can stop it.

HONESTY

Failures are reported

If the display cannot be created, or the tablet is not the authorized one, the app says so. It never fakes a working session.

02 — Architecture

What actually runs where

Two processes on the Mac, one app on the tablet. The host is Rust; the parts that need Apple frameworks are a small Swift library loaded over FFI.

macOS host

  • CGVirtualDisplay — creates the display
  • ScreenCaptureKit — captures that display
  • VideoToolbox — hardware H.264
  • CGEvent — injects pointer + scroll
  • Rust backend — protocol, session, adb, supervisor
→ video · 8890 ← input · 8891 USB · adb reverse

Android tablet

  • MediaCodec — hardware H.264 decode
  • SurfaceView — presents the stream
  • TouchCapture — sends pointer events
  • StreamingService — keeps it foreground
  • Upstream app, locally modified — same wire protocol
The private-API caveat, up front. A real extended display is created through CGVirtualDisplay, an unsupported CoreGraphics interface. It works on current macOS, it launches no kernel extension, and it can break in a future release. When it fails, UScreen reports the failure instead of quietly falling back to mirroring.

60 Hz is not 60 fps. The virtual display refreshes at 60 Hz; the frames captured per second depend on how much of the screen changes. In the 60-second motion benchmark the chain delivered 55.7 of 60 possible frames — the deficit sits at the animation-to-display-sampling boundary, not in the encoder. The honest label is 55.7/60 with an unproven cause.
What a product session actually reaches. In the preview.3 acceptance session — a normal, operator-initiated connection with no time limit — the chain captured 28.8–43.0 fps while a window was dragged and the tablet acknowledged 28.0–42.8 fps, with no blank and no dropped frames. The frame age was 15 ms at the median and the tablet's decode cost 29 ms per frame. The session ran for over eleven minutes and ended only when the operator disconnected it.
The benchmark is not what you will see. The 55.7 fps figure comes from a synthetic 1:1 motion benchmark. In live sessions at 1600×960 the rate follows how much of the screen actually changes: an earlier session measured about 12.3 captured and 12.1 acknowledged frames per second, and the preview.2 acceptance session measured 17.6–38.4 captured and 18.0–37.8 acknowledged frames per second while a window was being dragged, dropping to zero on a static desktop. All of these are real measurements under different conditions. None of them is 60 fps, and the capture rate — not the encoder, the transport or the tablet decoder — is what sets the ceiling.

06 — Limitations

Read this before you install

These are properties of the current design, not unfinished UI.

  • ExperimentalNo long-term stability claim. The longest session on the published preview.3 build lasted about eleven minutes; nothing has been run for hours or days.
  • Private APIThe display is created with CGVirtualDisplay, which Apple does not support and may change.
  • No resize in-processChanging resolution requires restarting the host; the display cannot be resized live.
  • H.264 onlyHEVC is not wired up. There is no codec negotiation.
  • No pen inputPressure, tilt and eraser are not implemented on macOS. Two fingers scroll; pinch does not zoom.
  • Graphics-stack careLong sessions stress ColorSync and WindowServer on the test machine. The supervisor watches and can stop a session.
  • Not notarizedSigned with a local self-signed certificate. macOS will require a per-app override on first launch.
  • Self-signed receiverThe Android APK is signed with a project-local key, not the upstream author’s. A tablet carrying an upstream build must uninstall it first; Android refuses a differently signed update.
  • Quarantine after a DisconnectIn the recommended build, an ordinary Disconnect can occasionally leave the machine in a quarantine state that blocks the next connection until an operator clears it. The cause is a race in the supervisor’s observation of the shutdown, and the fix is in the source and published in the development build — but that fix has not yet been accepted on hardware.
  • The development build is accepted, the Stable one is notThe experimental 0.3.0-rc.12 build completes real-hardware acceptance in the Development channel: the extended desktop was visible on the tablet, the tablet's decoder acknowledged the frames, a touch was injected into the extended display, and a transport reconnect reused the same display without growing the creation ledger. Nine defects were fixed to get there — the status panel that did not update while it was open, the panel that did not open on the first click, the machine's own swap churn vetoing every Connect, a backend refusal that was read as a success, a dead manager that read as a permission problem, the missing recovery, a second start that destroyed the live session, the handover that had no executable path, and a manager that mistook its own host for a second one. It is still a pre-release on the Development channel; keep the recommended build as the one you rely on.
07 — Install

Seven steps, one cable

The app installs user-level services into your home folder. No administrator password, no kernel extension, no system modification.

  1. Download the macOS application

    Take the .zip from the download section above. It contains the signed app bundle.

  2. Install and launch it

    Unzip it and put the bundle in your user Applications folder, then open it.

    mkdir -p ~/Applications
cp -R UScreen.app ~/Applications/          # UScreen-dev.app for the development build
open ~/Applications/UScreen.app

    The build is not notarized, so a double-click will be refused once. Right-click → Open → Open, or use System Settings → Privacy & Security → “Open Anyway”. Do not disable Gatekeeper or SIP.

  3. Download and install the Android receiver

    Install the .apk from the same release on the tablet. It is a separate application per channel, so the development receiver installs alongside the recommended one.

    brew install android-platform-tools   # if adb is missing
adb install -r UScreen-0.2.0-preview.2-android.apk   # recommended channel
adb install -r UScreen-0.3.0-rc.10-android.apk      # development channel

  4. Connect the tablet over USB

    Enable USB debugging, plug in a data cable, accept the RSA prompt, then check that exactly one device is listed. A charge-only cable is the most common setup fault.

    adb devices

  5. Grant Screen Recording and Accessibility

    Screen Recording (capture) and Accessibility (input injection) must be granted to the installed backend ~/Applications/UScreen/bin/uscreen-macos, then the app restarted.

    macOS attributes both permissions to the responsible process, and the backend runs as a launchd job. Use the menu-bar item Grant Permissions…: it asks the running manager to request them in its own process. A request raised from a terminal registers the terminal instead and never helps. Then allow the backend in System Settings → Privacy & Security → Screen & System Audio Recording and → Accessibility.

  6. Authorize the connection

    A Connect needs an operator authorization in addition to your approval: a lease that the menu issues on request, or uscreen-macos lease issue --serial <serial>. It is bound to one session and expires; it is not a permanent permission.

  7. Connect from the UScreen menu

    Menu-bar icon → Connect, then confirm the Touch ID prompt: it authorises one session. The session stays up until you disconnect, you unplug the tablet, or a genuine safety condition stops it — there is no time limit. Drag a window across and touch the tablet.

    ~/Applications/UScreen/bin/uscreen-macos stop
The development build starts differently. Installing it activates nothing. It needs a bounded session first: uscreen-macos dev start --authorize --serial <serial> (2 h, maximum 8 h), and uscreen-macos dev stop ends it.
Uninstall is symmetrical: uscreen-macos setup uninstall removes both LaunchAgents and the installed backend, and deleting ~/Applications/UScreen.app plus ~/Applications/UScreen removes the rest. Full detail in the installation guide.
08 — Security & privacy

What leaves the machine: nothing

SCOPE

Local sockets only

The video and input servers bind to loopback. Reachability comes from adb reverse, which is scoped to the attached device. There is no listening port on your network.

AUTH

Token before pixels

A client that does not present the 64-character token is dropped before the greeting. The token is delivered to the tablet through adb, not typed by you.

BINDING

One authorized device

An installation is bound to one ADB serial. A different tablet is refused at preparation, before the display is created, and during the session.

TELEMETRY

None

No analytics, no crash reporting, no accounts, no update pings. The site you are reading sets no cookies and loads no third-party scripts.

09 — Questions

Frequently asked

Is this the same project as UScreen for Linux?

It is a macOS port built on the same wire protocol and the same upstream Android app, with local changes to the receiver's streaming code. The Linux host uses EVDI, ffmpeg and uinput; on macOS those are replaced by CGVirtualDisplay, ScreenCaptureKit/VideoToolbox and CGEvent. The original Linux project is by majmichu1.

Why is macOS so insistent about opening it?

Because it is signed with a local certificate and not notarized by Apple. That is the honest state of a preview build without a paid developer account. Use the per-app override; do not turn off system security for it.

Does it work over Wi-Fi?

No. The transport is USB with adb reverse. Wireless adb is not supported and is refused where an authorization specifies USB.

Can I use more than one tablet?

One at a time. Each installation is bound to a single ADB serial; a second device is not silently substituted. Reinstall with the other serial to switch.

Why is the frame rate below my display's refresh rate?

Capture is damage-driven: it delivers frames when content changes, and the host's capture callback has a ceiling around 50–56 fps. The encoder is not the bottleneck — capture, encode, send and ACK stay 1:1. Your tablet's decoder sets the latency floor.

What is the difference between the recommended build and the development build?

The recommended build (v0.2.0-preview.3) is the last one that was verified on real hardware, and it is the one to use. The development build (0.3.0-rc.12) is published so that the newest fixes can be tried and problems reported.

They are separate installations, not two versions of one. The development build installs into ~/Applications/UScreen-dev with its own services, its own configuration and its own Android application (com.uscreen.dev). It does not update the recommended installation, and installing it changes nothing about it.

The development build is not yet fully hardware-tested and is not recommended as a replacement for the working version.

Can I go back to the recommended version after trying the development build?

Yes, and nothing has to be rebuilt. The recommended installation was never modified by the development build. Remove the development tree, its services and its Android app; the recommended release stays exactly where it was.

Where is the source code?

This repository hosts the site, the documentation and the release artifacts. The source is developed in a private repository and is not published here. The release includes a provenance record naming the exact commit it was built from, so claims in these docs can be traced.

Licence scope. The MIT licence in this repository covers what this repository publishes: the site, the documentation and the redistributed receiver build, including the upstream code it contains and the upstream copyright it preserves. It does not extend to the private macOS source, which carries its own licence file in its own repository.

Is there an Android APK in the download?

Yes. The same release carries UScreen-0.2.0-preview.2-android.apk (com.uscreen, Android 8.1+). It is signed with a project-local key, so a tablet that already has an upstream build has to uninstall it first. This exact APK is the one installed on the tablet in the acceptance session, and preview.3 did not change it.

The receiver is the upstream UScreen Android app by majmichu1 (MIT), taken from the upstream 1.2.10 release and modified locally in four Kotlin files (+370/−48 lines): the receiver no longer overwrites the negotiated frame rate and bitrate, streaming instability on real hardware was fixed, and the stream latency was lowered with a shallower capture queue and a measured ACK window. The upstream copyright is preserved.

12 — Release notes

What 0.3.0-rc.12 fixes, and what is still open

The development channel moves in small, verifiable steps. Every entry below came out of the operator's own hardware or out of the machine's own instruments, and every one of them has a regression test.

Release notes for 0.3.0-rc.12
AreaWhat changedHow it is verified
Android receiver The launch component was named com.uscreen.dev.MainActivity, but the development receiver is the same app with a different application id — the class stays com.uscreen.MainActivity. Every token relaunch failed and the tablet kept a stale token, so no video session ever authenticated. Read back from the built manifest: com.uscreen.dev · com.uscreen.MainActivity · versionCode 33 · signed v2 + v3 with the same project key as the previous release
Permissions macOS attributes Screen Recording and Accessibility to the responsible process. Only the launchd-run manager has the host's identity, so the menu now asks the manager to request them in its own process — and only on an explicit request. Architecture test: permission prompts come only from the manager, on request; the scan itself never prompts
Memory admission A swap-out burst alone no longer vetoes a start. The rule measures the memory the kernel can still hand out and calls a burst thrashing only when pages are evicted and faulted back at the same time. Below 512 MiB of allocatable memory a start is refused as a real shortfall. Regression tests: a burst with headroom is advisory, a burst without a headroom measurement stays a blocker, too little memory names the shortfall
Handover The Stable session that follows a handover is judged by the Stable supervisor against Stable's own band, not against the candidate's. A quieter Development baseline no longer makes the return to Stable look impossible. Regression tests over the handover plan, per judge
Manager lifecycle The session record is written before launchd starts anything, so the manager can no longer lose the race and leave a stale reading in the menu. Regression test: the session exists before the manager is kickstarted
Test isolation A unit test reached the real launchd and could boot your live services out — twice, each time killing the running host and its display. Every launchd mutation now goes through an injectable interface, and only the CLI hands out the real one. Architecture test: only main may reach the system launchd
Instrument The machine's own rate probe could not read its own output: 68 098 bytes is one byte over the pipe's capacity, and the runner waited for the child to exit first. Every probe was killed after 25 s, so the machine had no trusted rate window at all and both the admission gate and the quarantine recovery refused for the wrong reason. The query now completes in 1.45 s and returns the whole 68 KB; regression test: a child that outgrows the pipe is still read completely
Admission contract The band and the 300/min constant now judge what an operation adds, not what the machine already carries. The directly measured guards are unchanged and still live: ColorSync CPU at 50 % and memory pressure at level 4. Regression tests over the budget plan, with real measurements
Still open. The hardware acceptance of this exact build did not happen: every Connect was refused before anything was created (0 start attempts, 0 hosts spawned, the creation ledger unchanged), because the installed Development backend had no Screen Recording and Accessibility grant. The fixes above are therefore verified by regression test and code review — not by a completed video session. The build is published as a pre-release for exactly that reason, and it replaces nothing.
