01 — The short version

A display macOS believes in.

Most tablet-as-second-screen tools hand you a mirrored picture or a video stream inside an app. UScreen does what a physical monitor does: it registers a virtual display with the window server, the system lays windows out across it, and the pixels are captured, encoded and sent down the USB cable.

EXTEND

Extended, not mirrored

Windows can be dragged onto the tablet. The menu bar, Mission Control and window layout treat it as another screen, because it is one.

CAPTURE

Native capture pipeline

ScreenCaptureKit captures the display; VideoToolbox encodes H.264 with the media engine. No ffmpeg child process, no software encoder in the default path.

INPUT

Touch returns to the Mac

Taps, drags and two-finger scrolling on the tablet become real pointer and scroll events on the Mac, mapped to the virtual display's geometry.

TRANSPORT

One cable, local only

Video and input travel over adb reverse on loopback ports. Nothing is exposed to the network, and no cloud service is involved.

LIFECYCLE

Display that cleans up

The virtual display is removed when the host exits, and an independent supervisor watches the session and can stop it.

HONESTY

Failures are reported

If the display cannot be created, or the tablet is not the authorized one, the app says so. It never fakes a working session.

02 — Architecture

What actually runs where

Two processes on the Mac, one unmodified app on the tablet. The host is Rust; the parts that need Apple frameworks are a small Swift library loaded over FFI.

macOS host

  • CGVirtualDisplay — creates the display
  • ScreenCaptureKit — captures that display
  • VideoToolbox — hardware H.264
  • CGEvent — injects pointer + scroll
  • Rust backend — protocol, session, adb, supervisor
→ video · 8890 ← input · 8891 USB · adb reverse

Android tablet

  • MediaCodec — hardware H.264 decode
  • SurfaceView — presents the stream
  • TouchCapture — sends pointer events
  • StreamingService — keeps it foreground
  • Unmodified app — same wire protocol
The private-API caveat, up front. A real extended display is created through CGVirtualDisplay, an unsupported CoreGraphics interface. It works on current macOS, it launches no kernel extension, and it can break in a future release. When it fails, UScreen reports the failure instead of quietly falling back to mirroring.

60 Hz is not 60 fps. The virtual display refreshes at 60 Hz; the frames captured per second depend on how much of the screen changes. In the 60-second motion benchmark the chain delivered 55.7 of 60 possible frames — the deficit sits at the animation-to-display-sampling boundary, not in the encoder. The honest label is 55.7/60 with an unproven cause.
The benchmark is not what you will see. The 55.7 fps figure comes from a synthetic 1:1 motion benchmark; in an interactive session at 1600×960 the chain captured about 12.3 and the tablet acknowledged about 12.1 frames per second. Both numbers are real, they were measured under different conditions, and the gap has not been isolated. The tablet decoder and the cable are the usual suspects.

06 — Limitations

Read this before you install

These are properties of the current design, not unfinished UI.

  • ExperimentalNo long-term stability claim. Sessions have been run for tens of minutes, not days.
  • Private APIThe display is created with CGVirtualDisplay, which Apple does not support and may change.
  • No resize in-processChanging resolution requires restarting the host; the display cannot be resized live.
  • H.264 onlyHEVC is not wired up. There is no codec negotiation.
  • No pen inputPressure, tilt and eraser are not implemented on macOS. Two fingers scroll; pinch does not zoom.
  • Graphics-stack careLong sessions stress ColorSync and WindowServer on the test machine. The supervisor watches and can stop a session.
  • Not notarizedSigned with a local self-signed certificate. macOS will require a per-app override on first launch.
  • Self-signed receiverThe Android APK is signed with a project-local key, not the upstream author’s. A tablet carrying an upstream build must uninstall it first; Android refuses a differently signed update.
07 — Install

Six steps, one cable

The app installs user-level services into your home folder. No administrator password, no kernel extension, no system modification.

  1. Download and move the app

    Unzip and put the bundle in your user Applications folder.

    mkdir -p ~/Applications
cp -R UScreen.app ~/Applications/

  2. Approve the first launch

    The build is not notarized, so a double-click will be refused once. Right-click → Open → Open, or use System Settings → Privacy & Security → “Open Anyway”. Do not disable Gatekeeper or SIP.

  3. Connect and authorize the tablet

    Enable USB debugging, plug in a data cable, accept the RSA prompt, then check that exactly one device is listed.

    brew install android-platform-tools   # if adb is missing
adb devices
adb install UScreen-0.2.0-preview.2-android.apk   # receiver, same release

  4. Run the built-in setup

    Menu-bar icon → Set Up UScreen. It installs the backend, the native library and two user LaunchAgents. It creates no display and issues no authorization.

    ~/Applications/UScreen/bin/uscreen-macos setup install --activate \
  --serial <your-adb-serial> --profile low_latency

  5. Grant the two permissions

    Screen Recording (capture) and Accessibility (input injection) must be granted to the installed backend ~/Applications/UScreen/bin/uscreen-macos, then the app restarted.

  6. Connect

    Menu-bar icon → Connect. Confirm the Touch ID prompt if it appears. Drag a window across and touch the tablet.

    ~/Applications/UScreen/bin/uscreen-macos stop
Uninstall is symmetrical: uscreen-macos setup uninstall removes both LaunchAgents and the installed backend, and deleting ~/Applications/UScreen.app plus ~/Applications/UScreen removes the rest. Full detail in the installation guide.
08 — Security & privacy

What leaves the machine: nothing

SCOPE

Local sockets only

The video and input servers bind to loopback. Reachability comes from adb reverse, which is scoped to the attached device. There is no listening port on your network.

AUTH

Token before pixels

A client that does not present the 64-character token is dropped before the greeting. The token is delivered to the tablet through adb, not typed by you.

BINDING

One authorized device

An installation is bound to one ADB serial. A different tablet is refused at preparation, before the display is created, and during the session.

TELEMETRY

None

No analytics, no crash reporting, no accounts, no update pings. The site you are reading sets no cookies and loads no third-party scripts.

09 — Questions

Frequently asked

Is this the same project as UScreen for Linux?

It is a macOS port built on the same wire protocol and the same unmodified Android app. The Linux host uses EVDI, ffmpeg and uinput; on macOS those are replaced by CGVirtualDisplay, ScreenCaptureKit/VideoToolbox and CGEvent. The original Linux project is by majmichu1.

Why is macOS so insistent about opening it?

Because it is signed with a local certificate and not notarized by Apple. That is the honest state of a preview build without a paid developer account. Use the per-app override; do not turn off system security for it.

Does it work over Wi-Fi?

No. The transport is USB with adb reverse. Wireless adb is not supported and is refused where an authorization specifies USB.

Can I use more than one tablet?

One at a time. Each installation is bound to a single ADB serial; a second device is not silently substituted. Reinstall with the other serial to switch.

Why is the frame rate below my display's refresh rate?

Capture is damage-driven: it delivers frames when content changes, and the host's capture callback has a ceiling around 50–56 fps. The encoder is not the bottleneck — capture, encode, send and ACK stay 1:1. Your tablet's decoder sets the latency floor.

Where is the source code?

This repository hosts the site, the documentation and the release artifacts. The source is developed in a private repository and is not published here. The release includes a provenance record naming the exact commit it was built from, so claims in these docs can be traced.

Is there an Android APK in the download?

Yes. The same release carries UScreen-0.2.0-preview.2-android.apk (com.uscreen, Android 8.1+). It is signed with a project-local key, so a tablet that already has an upstream build has to uninstall it first. This exact APK has not been installed on hardware; the receiver code ran in earlier debug builds on the same device.
