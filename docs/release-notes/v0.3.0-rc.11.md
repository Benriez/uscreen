# UScreen 0.3.0-rc.11 — release notes

**Pre-release of the Development channel.** It supersedes `v0.3.0-rc.10`,
which stays published but should no longer be used.

> The receiver is **unchanged** since `v0.3.0-rc.10`: the Android application
> is the same APK (`UScreen-0.3.0-rc.10-android.apk`, `com.uscreen.dev`).

`v0.3.0-rc.10` carried the six defects the operator's tablet had found, but
it could not complete a session: every Connect was refused before anything was
created. This release fixes the two mechanisms that were still in the way, and
the hardware acceptance that was therefore open is now **closed for the
development build**.

### 1. The install never signed the backend (TCC identity)

macOS binds a Screen Recording / Accessibility grant to the *code identity* of
the running binary. The installer copied the raw build output, which is
ad-hoc signed and therefore has a different identity in every build — so every
reinstall silently lost the operator's grants, and the manager reported
"denied" while the terminal's own `doctor` reported "granted".

`setup install --sign-identity <SHA-1>` now signs the staged backend as
`com.uscreen.backend`, verifies it strictly and checks the designated
requirement (`identifier "com.uscreen.backend" and certificate leaf =
H"190764c7…"`) **before** it replaces the installed binary. A signing failure
leaves the previous installation byte-identical. The install marker records
the source *and* the installed digest, and an install without the flag warns
when the backend is not pinned to that identity.

### 2. The capture start was a blind 10 s guess

The start was bounded by a hardcoded wall-clock cap that had no relation to
the host's own startup budget. Under load a *progressing* start was torn down
mid-flight and reported as an opaque `-5`.

The start is now stage-aware (`shareable → configured → issued → settled`), an
errored start is distinguishable from a slow one, and the wait is bounded by
the host's **remaining startup window** — never more, and never a second
deadline of its own.

### 3. The ColorSync ceiling judged a decaying average

The supervisor stopped a host three seconds after the capture started, because
ColorSync read 67 % CPU. Measured on the operator's machine with no UScreen
host and no UScreen display at all: `ps` reported 63.3 % while the daemons were
using **18.6 %** of a core, and 55.6 % against 19.8 %. `ps`'s `pcpu` is a
decaying average over recent history — it reports what happened, not what is
happening.

The ceiling is unchanged (50 % of one core) and is now compared with the CPU
the daemons actually consumed between two supervisor ticks, read from their
cumulative CPU time. The average stays in the evidence as the corroborating
figure. The host's own pre-display safety gate measures the same rate: it used
to refuse a start with "ColorSync is already using 59 % CPU (limit 50 %)" while
the machine was using 19 %.

A critical reading **inside the host's startup window** is now a candidate
rather than a verdict: it is confirmed by the next reading on the supervisor's
own cadence. Two consecutive critical readings are a sustained condition and
stop the host exactly as before, and outside the startup window one critical
reading stops it as before.

### 4. Development-primary no longer depends on a stream count

The Development-primary consent waived the reversible-handover precondition
only while the Stable return was *already impossible* — which happens only at
eight streams. At seven streams the waiver did not fire while the handover plan
was refused, so the Development start was refused, so the machine never
reached eight streams: the selected operating mode could not be entered at all.

A valid consent now waives the handover precondition whenever it applies, and
it does not depend on the machine's current stream count. Every other control
— the attested observation, the per-display band, the absolute machine
ceiling, the rollback projection, the topology, ownership, Touch ID, the lease
and the creation budget — is still judged in full.

### Hardware acceptance (development build)

Verified on the operator's machine with this build:

| Item | Result |
| --- | --- |
| Virtual display | created at 1600×960, online, removed cleanly on Disconnect |
| Capture start | settled through every stage; H.264 at 1600×960 @ 60 fps |
| Video session | connected, codec config + IDR primed, frames acknowledged |
| Touch | the tablet's input channel authenticated; a touch moved the pointer |
| Transport reconnect | the tablet app was force-stopped and relaunched: the video session reconnected on the **same** display, the creation ledger did not grow |
| Operation | the session ran for hours with the supervisor healthy (ColorSync 9–21 %) |
