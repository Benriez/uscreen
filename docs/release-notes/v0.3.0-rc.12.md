# UScreen 0.3.0-rc.12 — the macOS development candidate

An Android tablet as a real, extended macOS display over one USB cable: a
virtual display created with macOS's own display stack, hardware H.264
encoding through ScreenCaptureKit + VideoToolbox, and touch handed back as
a graphics tablet.

This is the **Development channel** (`com.uscreen.menubar.dev`). It is a
separate installation from the recommended v0.2.0-preview.3 release and it
never replaces it.

## What this build fixes

Nine defects, all found on the operator's own hardware:

* **the status panel did not update while it was open** — the menu was
  rebuilt every two seconds, so an open menu kept the state it was opened
  with, and the reads ran on the main thread and froze the run loop that
  would have delivered the update. It is a popover now, updated in place.
* **the panel did not open on the first click** — a status-item popover is
  dropped when the app has not finished activating, so the show is now
  retried for a bounded moment.
* **the machine's own swap churn vetoed every Connect** on a loaded Mac.
  The rule now judges what a Connect *adds*, and the churn is an advisory
  the operator's approval covers. The real limits — critical memory
  pressure, a headroom below the floor — are unchanged.
* **a refusal from the backend was read as a success**, because the refusal
  text contains the word "loaded". The exit status decides now, and the
  refusal reaches the operator word for word.
* **a dead Development manager read as a permission problem.** The app
  answered "Permission status not verified (last status 8701s ago)" while
  macOS had said nothing about the permissions — there was simply no live
  manager to read them from. The permission states are now four (granted,
  denied, stale, unknown) and a stale reading can never be rendered as a
  verdict.
* **there was no recovery.** An absent manager is now brought back through
  the supported mechanism, which cannot extend the operator's authorization
  and never creates a second manager.
* **a second `dev start` destroyed the live session** — `launchctl bootstrap`
  answers an already-bootstrapped label with exit status 5, and the rollback
  that followed booted the running manager out.
* **the documented Stable → Development handover had no executable path.**
  It is a command now: `uscreen-macos dev handover --authorize`.
* **the manager mistook its own host for a second one** and reported no
  video while the picture was on the tablet.

## Measured on the DOOGEE U12, 2026-10-30

* the virtual display came up at 1600 × 960 beside the primary;
* the capture ran and the tablet's hardware decoder acknowledged the frames
  (2.0 fps, last acknowledgement 340 ms);
* the tablet's input channel authenticated and a touch was injected
  end-to-end in 18 ms;
* a cold Connect reached the first visible frame in 12.9 s of system time,
  with the operator's own wait excluded;
* a transport-only reconnect reused the same display — the creation ledger
  did not grow — and the host re-established the video session on it.

## Still open, stated plainly

* the previous receiver did not resume presenting frames after a transport
  loss in its tested window. The 0.3.0-rc.12 receiver did recover: the
  video session resumed at an IDR and the picture came back on the tablet.
  The warm-reconnect latency itself is still not measured;
* the build is signed with a local certificate and is **not notarised** —
  Gatekeeper will quarantine a downloaded copy until it is re-signed
  locally;
* the Stable channel is not offered yet.

## Install

    unzip UScreen-0.3.0-rc.12-macos-arm64.zip
    mv UScreen-dev.app ~/Applications/
    open ~/Applications/UScreen-dev.app

Then grant **Screen Recording** and **Accessibility** to
`~/Applications/UScreen-dev/bin/uscreen-macos` — the permissions belong to
that binary, not to the menu-bar app, and the installer refuses to publish
a backend it has not signed.

The receiver is a separate APK in this release and carries its own version
line. It is version 0.3.0-rc.13, version code 37, signed with the same
project key, so it installs over the previous development receiver without
uninstalling it and without losing the tablet's settings.

Three changes are in it. The upstream 1.2.11 behaviour that stops the
tablet from pushing its own frame rate and bitrate into the host's
configuration is carried over. The tablet keeps its waiting screen until a
frame has actually been presented. And the update check was repaired: it
asked the upstream Linux release feed and compared that project's version
line (1.2.x) against ours (0.3.0-rc.x), so every macOS receiver was told
that "Update 1.2.11 available" was waiting for it. It now reads the
UScreen for Mac releases, compares only version identifiers of its own
series, and offers a candidate only when the APK carries this channel's
own application id, this project's signing certificate and a higher
version code.
