# UScreen 0.3.0-rc.14 — the picture is on the tablet

An Android tablet as a real, extended macOS display over one USB cable: a
virtual display created with macOS's own display stack, hardware H.264
encoding through ScreenCaptureKit + VideoToolbox, and touch handed back as
a graphics tablet.

This is the **Development channel** (`com.uscreen.menubar.dev`). It is a
separate installation from the recommended v0.2.0-preview.3 release and it
never replaces it. It supersedes 0.3.0-rc.12 / the rc.13 receiver.

## What this build fixes

* **The tablet kept "Waiting for the first frame…" over a picture it was
  presenting.** The receiver's "first frame presented" signal fired only
  when its lifetime render counter was exactly 1 — once per app process,
  which lives for days — while the opaque waiting screen is raised on every
  disconnect. From the second session on, the Mac said "Video: Visible,
  streaming" and the tablet showed the waiting screen. The receiver
  (0.3.0-rc.14, version code 38) now arms a presentation gate per video
  session and per decoder and takes the screen down on that session's first
  presented frame.
* **The Mac's "Visible" was a one-shot claim.** The host's video state is
  now session-scoped: a new video session clears the previous session's
  evidence; every sent frame and every presentation report are recorded; a
  sent frame with no presentation report for 5 s becomes `stalled`; the last
  receiver session closing publishes `none`. The popover says "picture
  stalled" instead of "streaming" in that case, and its headline wraps
  instead of running into the rows.
* **Every Connect was stopped after about two minutes.** The display coming
  online reset the ColorSync collector's delivery-coverage chain, the rate
  was UNKNOWN for two more queries, and the supervisor stopped the host for
  missing telemetry. Display topology no longer resets the chain; only a
  dead reader, a new boot session or a new producer image do.
* **A quiet, resident ColorSync producer refused every start.** A zero
  machine-wide rate is now verified through live delivery controls read back
  through a continuously live `log stream` subscription, with the retained
  live records as the measurement once coverage is complete. The first
  trusted value takes about 70 s instead of 129 s.

## Confirmed on the DOOGEE U12, 2026-11-02

* the virtual display came up at 1600 × 960 and the measurement stayed VALID
  (24 profile events/min with two displays), no incident;
* the first frame was presented 2.0 s after the first keyframe; the operator
  confirmed the real extended desktop on the tablet;
* the session ran past the former two-minute failure point (4 min) until the
  Mac slept; the host then stopped itself when the device had been gone for
  31 s — the intended safety path.

## Still open, stated plainly

* touch, a controlled reconnect and a ten-minute sustained session are not
  yet re-accepted on this exact build;
* the live measurement cannot observe unified-log loss records (`log
  stream` has no `--loss`); the bootstrap archive query can;
* the build is signed with a local certificate and is **not notarised**;
* the Stable channel is not offered yet.

## Install

    unzip UScreen-0.3.0-rc.14-macos-arm64.zip
    mv UScreen-dev.app ~/Applications/
    open ~/Applications/UScreen-dev.app
    adb install -r UScreen-0.3.0-rc.14-android.apk

Then grant **Screen Recording** and **Accessibility** to
`~/Applications/UScreen-dev/bin/uscreen-macos` and start a bounded session
with `uscreen-macos dev start --authorize --serial <adb serial>`.
