# 0.3.0-rc.10 — Development channel

Released 2026-10-28 as a pre-release. Not hardware-accepted. Not a replacement for
`v0.2.0-preview.3`.

**Pre-release of the Development channel.** Not hardware-accepted, not a
replacement for `v0.2.0-preview.3`.

> Supersedes `v0.3.0-dev.3`, which stays published but should no longer be
> used. Same channel, same installation layout, same Android application id.

This release carries the six defects the operator's own tablet found, plus the
two that the machine's own instruments found. Every one of them is covered by
a regression test; the counts are in `PUBLICATION_BUILD.json`.

### 1. The tablet could not authenticate

The receiver is the same Android application as the production one with the
application id `com.uscreen.dev`; its Gradle `namespace` stays `com.uscreen`,
so the activity class is still `com.uscreen.MainActivity`. The candidate
named it `com.uscreen.dev.MainActivity`, so every token relaunch failed and
the tablet kept a stale session token — no video session ever authenticated.
The launch component is now `com.uscreen.dev/com.uscreen.MainActivity`.

### 2. The macOS permissions could not be granted

macOS attributes Screen Recording and Accessibility to the *responsible
process*. The only process with the host's identity is the launchd-run
connection manager, so a prompt raised from the menu or from a shell
registered the wrong binary — which is why the permissions stayed denied for
the backend path. The menu's **Grant Permissions…** now asks the running
manager to request them *in its own process*. It changes no privacy entry by
itself: macOS asks, the operator answers.

### 3. A swap-out burst vetoed every start

On a routinely loaded Mac the memory rule read a burst of swap-outs as
"thrashing" and refused every start, although 4 GiB could still be allocated.
A burst alone is normal compressor work. The rule now measures the memory the
kernel can still hand out (`kern.memorystatus_level` × `hw.memsize`) and only
calls a burst thrashing when pages are evicted *and* faulted back at the same
time. Below 512 MiB of allocatable memory a start is refused as a real
shortfall, and the refusal names the numbers. Without a headroom measurement
the old rule still applies — nothing is relaxed blind.

### 4. A reversible handover was refused on a false premise

The Stable session that follows a handover is judged by the Stable supervisor,
against Stable's own recorded band — not against the candidate's. A quieter
Development baseline (24/min) made the return to Stable (72/min) look
impossible although Stable would have accepted it. Each step of the handover
plan is now judged by the supervisor that will actually judge it, and the
absolute ceiling still applies to every step.

### 5. The manager sometimes started before its session existed

The session record is now written *before* launchd starts anything, so a
kickstart that wins the race exits with "not started" instead of leaving the
menu showing a permission reading from an earlier session. A failed
activation clears the record again.

### 6. A unit test could boot the operator's live services out of launchd

The uninstall test reached `SystemLaunchd` directly while every path it
touched was a temporary root. It booted the live Development supervisor and
manager out of the real launchd — twice, each time killing the running host
and its display. Every launchd mutation now goes through an injectable
`Launchd` trait, and only `main` hands out the real implementation. An
architecture test holds that line.

### 7. The machine's own rate probe could not read its own output

The supervisor's rate query returns 68 098 bytes on this machine — one byte
more than the pipe's capacity. The runner waited for the child to exit
*before* reading the child's stdout, so `log show` blocked writing to a full
pipe and never exited: every probe was killed after 25 s and published
nothing. The machine therefore had no trusted rate window at all, and both
the admission gate and the quarantine recovery refused for a reason that had
nothing to do with the machine. The drain is now non-blocking and happens in
the same loop that waits for the child. The query now completes in 1.45 s and
returns the whole 68 KB.

### 8. The admission judges what an operation *adds*

The band (96.6/min) and the 300/min constant now judge the churn an
operation adds, not the machine's cumulative total. The directly measured
guards are unchanged and still live: ColorSync CPU at 50 % and memory
pressure at level 4.

### 9. The menu restarts a supervisor that closed itself

If the supervisor closed itself on a critical reading, the Development menu
used to hand the Connect to a manager that could only refuse. It now
restarts the supervisor first.

## Verification

- **1197** hardware-free Rust tests pass, **1199** in the hardware build.
- The menu bar's own self-test passes (`SELFTEST OK`).
- `codesign --verify --strict`: 4/4 (bundle, backend, menu bar, native
  library), pinned to the local identity `UScreen Local Code Signing`.
- The APK is signed with the **same project key** as the previous
  development release (certificate SHA-256 `c19de7ad…`), so it installs over
  it in place; verified with APK Signature Scheme v2 + v3.
- The shipped backend contains **0** occurrences of the build machine's home
  directory; the native layer resolves only through `@rpath`.
- The published bundle was **not** installed on the operator's machine as
  part of this release; the running installation was not touched.

## Known limitations

- **The hardware acceptance run of this exact build is still open.** The
  session itself was never completed: the operator's Development backend had
  no Screen Recording and Accessibility grant, and every Connect was refused
  *before* anything was created (0 start attempts, 0 hosts spawned, the
  creation ledger unchanged). The fixes in this release are therefore
  **verified by test and by code review, not by a completed video session**.
- **Not notarized.** The app is signed with a local self-signed identity;
  macOS asks you to allow it the first time you open it.
- **Apple Silicon only, USB only.** No Intel build, no Wi-Fi transport in
  this candidate.
- **No OS sandbox.** Both channels run as your own user; the isolation
  between them is application-level.
- Amazon Prime Video and other DRM-protected playback may show black video
  while UScreen is active.
- The recommended installation `v0.2.0-preview.3` can still enter a
  quarantine after a normal Disconnect. The source corrects that race; the
  correction has not yet been accepted on real hardware.

## What this release is not

It is not Stable. It is not a replacement for `v0.2.0-preview.3`. It does not
promote anything, change no threshold, and disables no safety check.
